Study of `~/workspace/rara-pos-desktop/` (read-only, 2026-11-17). RARA POS is at
version **1.1.10**; the Sahara app is **v1.0.0** and copies these conventions,
with the deltas listed in §8. All paths below are relative to
`~/workspace/rara-pos-desktop/` unless stated otherwise.

> `~/workspace/custom-skills/desktop_app_release_delivery/SKILL.md` — verify the
> installer + feed file exist before announcing; offer the working download
> route first (temporary-public repo + PowerShell `curl` to Desktop, repo

**Renderer architecture:** classic `<script>` tags (no bundler, no framework),
each module an IIFE registering into `window.Screens.<name>`; `window.App`
is the shared contract (`{state, user, theme, go, notify, money, branchName,
stockOf, canSeeCost, can, currentBranchId, save}`). Every module loads DB with
the same fallback, because a relative `require('./db.js')` inside a classic
script resolves against `index.html` (project root), not the file:

```js
const DB = (function () { try { return require('./db.js'); } catch (e) { return require('./src/db.js'); } })();
DB.load();
```

`DB.load()` is called once per renderer module, on the **same** DB object —
hence the sticky flags in §3. No remote content is ever loaded; the window
only loads the bundled local `index.html`. Fully offline: system fonts only,
no CDN (`styles.css:1`).

## 2. `main.js` — main process

### Window creation (`createWindow`, lines 251–280)
- `BrowserWindow` 1280×800, icon `build/icon.png`,
  `webPreferences: { nodeIntegration: true, contextIsolation: false }`
  (renderer uses Node `require` directly — no preload, no context bridge).
- `Menu.setApplicationMenu(null)` — no default app menu; in-app navigation only.
- `win.loadFile(index.html)`; `win.on('close', () => backupOnClose())`.
- `app.on('window-all-closed')`: quit on Windows/Linux, stay alive on macOS.
- Before the window is created, `process.env.RARA_DATA_DIR = app.getPath('userData')`
  (lines ~284–288) — the renderer cannot call `app.getPath()` itself, so the
  data folder is handed over through the environment; `src/db.js` reads it first.

### `backupOnClose()` (lines 217–249)
Synchronous, in the window `close` handler; any failure is swallowed so it can
never stop the app closing. v1.1.9 guard (the 2026-11-15 lesson):
1. If the data file doesn't exist → return.
2. Parse it; if it doesn't parse → return (never back up a corrupt file).
3. If `products == 0 && appUsers == 0` → return (never back up an empty file —
   an empty close-backup would become the "newest" backup and the next restore
   would bring back nothing, and pruning to the last 7 would push a good
   backup out).
4. Copy to `<userData>/backups/rara-pos-backup-YYYY-MM-DD_HH-MM-SS-mmm.json`,
   verify the copy parses, prune to the **last 7** by mtime.

### Printing — measured-height thermal (`ipcMain.handle`, lines 181–214)
CSS alone cannot size a thermal page (`@page size:80mm auto` is invalid in
Blink; a square 80mm page split a 3-item bill across 2 pages). So:
- **Renderer** (`src/pos.js:149–196`): renders the receipt HTML into the hidden
  `#receipt-print` div, temporarily shows it off-screen (`visibility:hidden`,
  `position:absolute; left:-9999px`, width `72mm`), measures
  `getBoundingClientRect().height`, converts px → microns:
  `heightMicrons = round((heightPx * 25.4/96 + 6) * 1000)` (+6mm trailing feed
  for the cutter).
- **Main** `print-receipt` (lines 188–214): validates
  `20000 ≤ height ≤ 600000` microns and a non-empty `deviceName`, then
  `mainWin.webContents.print({ silent: true, deviceName, pageSize: { width: 72000, height }, margins: { marginType: 'none' }, printBackground: false, copies: 1 })`.
  Returns `{ok:true}` / `{ok:false, error}` — raw errors are never surfaced
  (they can contain paths); the renderer shows a short Roman Urdu notice.
- `printer-list` (lines 181–186): `webContents.getPrintersAsync()` →
  `[{name, displayName, isDefault}]`. The Owner picks the printer once in
  Settings; it is stored in `settings.printerName`.
- Renderer fallback: no printer set, no IPC, or print failure (except a
  12-second timeout, where the silent job may still come out — so the dialog
  is deliberately NOT opened, or the bill would print twice) → `window.print()`
  dialog (`src/pos.js:162–195`).

### IPC surface (all of it)
| Channel | Direction | Purpose |
|---|---|---|
| `printer-list` (handle) | renderer → main | System printer list |
| `print-receipt` (handle) | renderer → main | Silent measured-height thermal print |
| `update-get-state` (handle) | renderer → main | Updater state (version, token saved?, auto-check, last check, status) |
| `update-check-now` (on) | renderer → main | Manual update check |
| `update-save-token` / `update-clear-token` (on) | renderer → main | Store/remove the GitHub token |
| `update-set-auto-check` (on) | renderer → main | Auto-check on/off |
| `update-quit-install` (on) | renderer → main | `quitAndInstall(false, true)` |
| `update-event` (send) | main → renderer | `status` / `no-token` / `available` / `none` / `progress` / `downloaded` / `error` |

### Auto-update code (lines 8–179) — **OMIT ALL OF THIS for Sahara v1.0.0**
- `electron-updater` (optional require, `autoUpdater = null` if absent),
  `UPDATE_OWNER`/`UPDATE_REPO` constants, `update-token.json` /
  `update-state.json` in `userData`, `setFeedURL({provider:'github', private:true, token})`,
  `autoDownload = true`, `autoInstallOnAppQuit = false`, `allowPrerelease = false`,
  progress notices bucketed per 10%, delayed first check 8s after
  `did-finish-load` (packaged app + auto-check ON only).
- Token model (private repo): Owner pastes a fine-grained read-only PAT once
  in Settings → Updates; stored ONLY in `<userData>/update-token.json`, never
  in repo/code/logs; missing token → graceful Roman Urdu notice, never a crash.
- **Sahara v1.0.0 omissions:** the `electron-updater` dependency, the whole
  lines 8–179 block, all `update-*` IPC channels, `App.initUpdateBridge` /
  `renderUpdateStatus` / `checkForUpdates` / `installUpdate` in `src/ui.js`,
  and the Updates card in `src/settings.js`. Delivery is by manual installer
  download (PowerShell) only — see §7. Do **not** ship a `latest.yml` feed
  consumer; if the `publish` block is kept in `package.json` it is only so the
  workflow can attach the installer to a GitHub Release for manual download.

## 3. `src/db.js` — data-safety hardening (v1.1.9, the core to copy)

### Paths & constants (lines 67–93)
```js
// 1st choice: process.env.RARA_DATA_DIR (set by main.js from app.getPath('userData'))
// 2nd: electron.app.getPath('userData') if required from main process
// 3rd: ./data next to db.js (plain-node tests only)
const DATA_FILE  = path.join(dataDir, 'rara-pos-data.json');
const BAK_FILE   = DATA_FILE + '.bak';
const BACKUP_DIR = path.join(dataDir, 'backups');
const SEED_FILE  = path.join(__dirname, 'seed.json');
const MAX_BACKUPS = 7;
```
On a real Windows install the live data is
`%APPDATA%\<appId>\rara-pos-data.json` (appId `com.rara.pos` → folder
`com.rara.pos` under `%APPDATA%`). **Sahara rename:** `SAHARA_DATA_DIR`,
`sahara-bakers-data.json`, backup prefix `sahara-bakers-backup-`.

### State shape
`products, branches, sales, purchases, customers, suppliers, expenses,
employees, transfers, stockMovements, cashSessions, appUsers, loginSecurity,
settings`. Product: `{id, name, price, purchasePrice, wholesalePrice,
franchisePrice, size, category, brand, sku, barcode, notes, lowThreshold,
status, stock, branchStocks:[{branchId, qty}], image}`. Stock is per-branch
(`branchStocks`); `stock` is the recomputed total (`recalcProductStock`).
Branch ids are **numbers** in state; `<select>` values are strings — `App`
normalises with `normBranchId()` (`src/ui.js`) so `DB.stockOf`'s strict
`===` lookup works. User: `{id, name, username, pinHash, role, branchId,
branchName, isActive}`.

### `DB.load()` (lines 282–~470) — recovery order
Flags on the DB object (lines 135–136): `recoveredFromBackup: false`,
`loadError: null`. **Sticky by design** (comment lines 283–288): `load()` runs
once per renderer module on the same object, so a later clean re-read of the
just-recovered file must NOT wipe the first load's recovery report before
`App.init()` shows it. A load that recovers/fails overwrites the flags; a clean
load leaves them exactly as they were.

Order of attempts:
1. **Data file exists and parses:**
   - If `products.length == 0` (the 2026-11-15 empty-state start — trigger is
     products == 0 **alone**, not products == 0 AND users == 0, because the
     user's laptop already had an Owner login he created after the loss):
     1. `applyFreshSeed()` (below) if `settings.v119FreshSeedApplied` is not set;
     2. else `recoverFromGoodBackup('Khaali data mila')`;
     3. else stay empty with
        `loadError = 'Khaali data mila aur koi acha backup nahi mila — Backup se restore karein ya naya data add karein.'`
   - If products > 0: normal load, flags untouched.
2. **Data file corrupt (parse throws):** try `.bak` → success sets
   `recoveredFromBackup = true`, `loadError = 'Main data file kharab thi — pichli achi copy (.bak) se data wapas laya gaya hai.'`, then `this.save()`
   (safe here: the in-memory state is good, so `.bak` may be refreshed).
   If `.bak` also fails → `recoverFromGoodBackup('Data file kharab thi')` →
   else `applyFreshSeed()` if flag unset → else empty state with
   `loadError = 'Data file kharab thi aur backup bhi nahi mila — khaali data se shuru kiya gaya hai. Backup se restore karein.'`
3. **No data file, seed exists:** load `seed.json` (delete its `_note` key),
   set `settings.v119FreshSeedApplied = true`, `save()`.
4. **Neither:** empty state + `save()`.
5. Then one-time flag-guarded migrations (each writes once, flag stops the
   record coming back if the Owner later deletes it): `townshipLoginSeeded`
   (adds `township` / Franchise / branch 3 / PIN 1234, line ~424),
   `salesmanLoginSeeded` (adds `salesman` / Salesman / branch 2 / PIN 1234,
   line ~446), `billAddressesSeeded` (branch 2/3 receipt addresses), plus
   `settings.sessionTimeoutMinutes` default 15.

### `newestGoodBackup()` (lines 936–959)
The 2026-11-15 lesson: **never trust the newest backup blindly** — it was
itself the empty state. Scans `backupInfo()` newest-first, parses each, skips
unparseable / wrong-shape files; returns the first with `products.length > 0`
(`{ok, name, at, state, products, sales, logins}`). If none has products, falls
back to the newest backup with `appUsers.length > 0` (login-only fallback).
Returns `{ok:false}` if nothing qualifies.

### `restoreLatestBackup()` (lines 961–~985)
1. No backup files at all → `{ok:false, message:'Koi backup nahi mila — pehle backup banayein.'}`
2. Read the good backup into memory **first** (the safety backup in step 3
   writes a new file and prunes to 7, which must never push the good backup
   out before it is read).
3. `this.backup()` as a safety copy of the current (possibly broken) state.
4. `this.state = good.state`; ensure `sessionTimeoutMinutes` default; `save()`.
5. Returns `{ok, at, name, products, sales, logins}`; no good backup →
   `'Koi acha backup nahi mila — tamam backups khaali hain ya kharab hain.'`

### `_saveRecovered()` (lines 497–502) vs `save()` (lines ~475–493)
- `save()`: atomic — rebuild indexes, write `DATA_FILE + '.tmp'`, then copy the
  previous good file to `.bak` (**only if it parses**), then `renameSync` tmp
  over the real file. A crash mid-write never leaves a half file.
- `_saveRecovered()`: same atomic tmp+rename write but **never touches `.bak`**.
  Used after every recovery/seed: the file on disk is corrupt or empty and
  must never become the "last good" `.bak` copy. This is the single most
  important invariant to copy.

### `DB.backup()` (lines 883–911) / `DB.backupInfo()` (lines 913–933)
`backup()`: timestamped `rara-pos-backup-YYYY-MM-DD_HH-MM-SS-mmm.json`
(same-millisecond collision gets a `-n` suffix), writes the whole state,
**verifies by reading it back and parsing** (and checking `products` is an
array — a backup that can't be read back is not a backup), prunes to
`MAX_BACKUPS = 7`. Also called once a day right after login (`src/ui.js`
`login()`) and from Settings → Backup Now. `backupInfo()` returns
`{lastBackup, count, files:[{name, path, at, size}]}` newest-first.

### Seed / migration pattern — `applyFreshSeed()` (lines 315–349)
One-time fresh-seed migration, flag-guarded by
`settings.v119FreshSeedApplied`:
- Reads `seed.json`, deletes `_note`, replaces state with the seed.
- **Merges existing users — never replaces them:** existing users go first; a
  seed user is skipped when its username already exists (case-insensitive);
  the seed Owner is skipped when an existing user already has the Owner role
  — *his PIN wins, so there is never a second Owner*.
- Preserves old settings, then sets `v119FreshSeedApplied: true`.
- Sets `recoveredFromBackup = true`,
  `loadError = 'Naya data load ho gaya hai — 12 products aur logins tayyar hain.'`
- Persists via `_saveRecovered()` (never `.bak`-touching `save()`).
- Once applied, later losses auto-recover from a good backup instead of
  re-seeding. **Sahara rename:** flag e.g. `v100FreshSeedApplied`, seed with
  Sahara's 44 items / 3 branches / logins. Note the Sahara web app is
  password-free — if the desktop keeps that, the seed still needs its logins
  (Owner Rahmanullah etc.) but the login screen is skipped; decide this
  explicitly and keep the PIN/lockout code intact underneath so a password
  can be put back later.

### Other DB API worth copying verbatim
- **Indexes** (`buildIndexes`, in-memory only, never serialised): Maps for
  `productById/Sku/Barcode`, `branchById`, `customerByPhone`, `supplierById/Name`,
  `saleById/ClientRef`, `userByUsername`, `maxId` per collection (O(1)
  `nextId`), `salesByBranch` / `movementsByBranch` (date-sorted, `'all'` key
  holds every row once). `salesInRange(fromISO, toISO, branchId)` uses the
  index; legacy null-branch rows are included for every branch filter.
- **Idempotent sales** (`createSale`): `clientRef` (`'sale-' + Date.now().toString(36) + '-' + random`)
  — a double-submit/double-click with the same ref returns the existing sale,
  `{created:false}`, so stock is never deducted twice.
- **Netting (v1.1.6, one place so Dashboard / Sales History / Reports agree):**
  `isSuccessfulSale` (not cancelled/fully-returned), `returnsRefund`,
  `returnedQty`, `netSaleTotal = max(0, total − refunds)`, `productWise(sales,
  products, costBasis)` — only successful sales count; partial returns subtract
  only the returned part; cost 0 is never invented (`costZero` flag → plain UI
  note). `ownerUnitCost` (purchasePrice) vs `franchiseUnitCost` (franchisePrice).
- **Uniqueness** (`checkUniqueness`, `findDuplicates`): data-layer duplicate
  guards with Roman Urdu messages (SKU, barcode, customer phone, supplier
  name, username, branch name); empty values ignored; `findDuplicates` reports
  only, never deletes.
- **Role-aware data** (`costOf`: purchase price Owner-only, else 0;
  `sanitizeState`: strips prices/suppliers/purchases/logins per role, PIN
  hashes never included for any role; Franchise keeps only its own branch's
  rows; `requireRole` throws a Roman Urdu permission error).
- **Stock:** `stockOf(product, branchId?)`, `setStock` (clamps ≥ 0),
  `addMovement` (keeps the movement index in step), `recalcProductStock`.
- **Transfer bill values** (`transferBillValues`): per-item franchise + sale
  values from current prices, `franchiseZero` flag → plain note.

## 4. PIN hashing & login / lockout

- **Hash** (`src/db.js:515–522`): `hashPin(pin) = sha256(String(pin) + ':rara-pos-salt')`
  as hex (Node `crypto`, unsalted-per-user — one fixed salt string; **Sahara:
  change the salt string**, e.g. `':sahara-bakers-salt'`). `checkPin(user, pin)`
  compares `user.pinHash === hashPin(pin)`. PINs are stored hashed only;
  default seed PIN is `1234` for all three logins and the Owner must change
  them in-app (seed `pinHash` for `1234` is
  `9b2680285f0d118e9cd5c057a3f292083b655b9c218e7cc39896da4426cac3f7`).
  PIN format enforced in UI: 4–6 digits (`/^\d{4,6}$/`), `maxlength="6"`,
  `inputmode="numeric"`.
- **Lockout** (`src/db.js:524–~590`): `LOCKOUT_AFTER = 5`, `LOCKOUT_MINUTES = 15`.
  Per-username `{attempts, lockedUntil}` in `state.loginSecurity` — **persisted
  in the data file, so restarting the app does NOT reset the counter or the
  lock**. `isLoginLocked(username)` (expired lock auto-clears + saves),
  `recordFailedLogin` (locks at 5, saves), `recordSuccessfulLogin` (clears the
  record). No reset path except waiting it out (or a successful Owner login
  resetting that Owner's own counter). UI (`src/ui.js` login submit): locked
  login shows remaining minutes; 5th wrong PIN → `'5 ghalat PIN — ye login 15
  minute ke liye lock ho gaya hai'`.
- **Login flow** (`src/ui.js` `renderLogin` / `login`): pick a user button →
  PIN → `DB.checkPin`. Zero users → Owner Setup form (name, username, PIN,
  PIN-confirm; no default PIN). Successful login: welcome notice, idle timer
  starts, once-a-day auto-backup check, then route by role (Franchise →
  `franchise`, Salesman → `salesman`, else `dashboard` if permitted, else
  `pos`). **Session timeout:** default 15 min (`settings.sessionTimeoutMinutes`,
  5–120), warning notice 1 minute before locking; lock keeps data + branch,
  only the PIN screen returns, and the locked user is pre-selected.
- **Roles** (`src/ui.js` `can()` / `OWNER_ONLY`): Owner can do everything;
  Manager: dashboard/sale/return/products/stock/sales/customers/expenses/cash;
  Cashier: sale/return/stock/sales; Franchise: franchise-dashboard/sale/return/
  products/stock/sales (own branch only); Salesman: salesman-dashboard/sale/
  return/products/stock/sales (own branch only, no cost/profit anywhere).
  `OWNER_ONLY = ['sale-cancel','settings','reports','purchases','suppliers','logins']`.
  Non-Owners are locked to their own branch (header branch dropdown lists
  only that branch and is disabled).

## 5. UI conventions

- **Top notices** — `App.notify(msg, type, action?)` (`src/ui.js:825–842`):
  `#notice-stack` (`aria-live="polite"`, fixed top, z-index above modals).
  Auto-dismiss **9 seconds** (`setTimeout(dismiss, 9000)`) with a countdown
  progress bar (`.notice-bar`, CSS `animation: notice-countdown 9s linear
  forwards`, `styles.css:189–196`) and an × button. Types: `success` (green/
  accent left border), `error` (red), `warning` (amber), `info` (teal).
  Optional `action: {label, onClick}` adds one button (used by the
  update "Restart Karein" prompt — omit with auto-update). All user-facing
  messages are short Roman Urdu; errors are sanitised (hashes/long tokens
  replaced with `[hidden]`, capped at 160 chars) and never show stack traces.
  Global `window.onerror` / `unhandledrejection` handlers route everything
  through the notice — no blank screens.
- **Login-screen ⋮ menu** (`index.html` login card; wired in `App.init`,
  `src/ui.js` ~205–240): top-right ⋮ button; dropdown with theme toggle,
  **"Backup se Data Wapas Layein"** (one-click restore, no login needed —
  `restoreFromLogin()`, `src/ui.js:727–740`, restores the newest GOOD backup
  and re-renders the login screen with counts), and **"Branch Badlein"**
  (v1.1.10, resets the branch choice — see below). Closes on outside click.
- **Branch selector (v1.1.10)** — `localStorage` key **`rara-pos-login-branch`**,
  values `'all' | 'outlet' | 'town'` (semantic, not numeric ids, so they
  survive branch-id changes). `loginBranchChoice()` / `setLoginBranch()` /
  `loginsForBranch()` (`src/ui.js:569–~600`): `'town'` shows ONLY the Township
  login; `'outlet'` shows Owner + Outlet logins; `'all'` shows every login.
  Persisted per device, so the Township laptop stays Township-only; "Branch
  Badlein" is the discreet way back. If the chosen branch has no login at all,
  the selector comes back so nobody is stuck. **Sahara:** same key pattern
  with a Sahara key name (e.g. `sahara-login-branch`) if a branch-scoped
  login screen is wanted; otherwise omit.
- **Theme toggle** — `localStorage` key **`rara-pos-theme`** (`'dark'|'light'`,
  default dark). `body[data-theme]` drives CSS variables; header/login logos
  swap (`assets/rara-logo-dark.png` ↔ `assets/rara-logo-light.jpg`, with
  `onerror` fallback to a text logo). Dark theme: warm brown-black over the
  live video background (paused + hidden in Light theme and when
  `settings.liveBackground` is OFF). Toggle button text flips
  ("Light Mode" ↔ "Dark Mode"). Sahara already has a black-and-white theme
  from the web app — keep the same toggle mechanism, swap the variable sets.
- **Bill preview / print flow** (`src/pos.js:226–281`, `index.html`
  `#bill-preview-overlay`): after a sale completes, the bill is **shown first**
  in a modal rendering the SAME `receiptHtml(sale)` that printing uses, so
  preview and printed bill always match. "Print Karein" → measured-height
  print (§2); on success the modal closes, on failure it stays open so the
  user can retry or close without printing. Reprint from Sales History;
  transfer bills reuse the same modal via `showBillPreviewHtml(html, printFn)`
  (`src/transfer-bill.js`). Receipt layout: exact logo ~40mm wide
  (`.r-logo`, `styles.css:305`), "Fragrance / Fashions", **only the sale
  branch's address line** (no branch name), 13px weight 700, 72mm width.
  Print CSS (`styles.css:289–308`): `#receipt-print { display:none }` on
  screen; `@media print` hides everything except `#receipt-print` at 72mm.
  Bill numbers: sales `R-0001…`, transfers `T-0001…` (derived from `nextId`).
- **Confirm dialog** — in-app overlay (`#confirm-overlay`, `App.confirmDialog`
  returns a Promise) instead of `window.confirm`; used for cancel-sale,
  return, restore, import, update-install.
- **Shell layout (v1.1.10 fix)** — `.app-shell { height: 100vh; display:flex;

  Sale screen's sticky cart work (below); a window-level scroller traps
  `position: sticky` — the 1.1.10 tests caught exactly this bug.
- **Sale sticky side cart (v1.1.10)** — two-column `.pos-layout`: product grid
  left, `.pos-cart { position: sticky; top: 0; max-height: calc(100vh - 150px) }`
  right (`styles.css:247`); cart lines + customer + payment live in the

  and the "Sale Complete Karein" button is pinned at the panel bottom

- **Money:** `App.money(n)` → `'Rs ' + toLocaleString('en-US')` (2 decimals

- **Online/offline badge:** header `#net-badge` — `Online` / `Offline — Local`,

  online/offline + sync concept — the desktop is local-first; sync, if any,

## 7. Test harness

Two layers; both live in the evidence folders, not in the app repo.

### Node DB tests — `~/workspace/rara-pos-119-test-evidence/db-test.mjs` (18/18), `db-test-seed.mjs` (8/8); v1.1.10: `~/workspace/rara-pos-1110-test-evidence/db-test-1110.log`
- Plain `node <file>.mjs` (Node 24). No Electron, no test framework — a tiny
  `log(name, pass, detail)` helper printing `PASS | …` / `FAIL | …` and a
  `==== SUMMARY: N/N passed ====` line at the end.
- Isolation: each case gets a fresh temp dir via `fs.mkdtempSync(os.tmpdir() +
  'rara-pos-119-db-')`; the test sets `process.env.RARA_DATA_DIR = dir` **before**
  requiring `db.js`, then writes crafted `rara-pos-data.json` / `.bak` /
  `backups/*.json` files into it (corrupt JSON, empty state, good backup,
  newer empty backup, login-only backup) and asserts `DB.load()` /
  `newestGoodBackup()` / `restoreLatestBackup()` outcomes, including the exact
  `loadError` strings and that `.bak` still holds the good state after an
  empty-state recovery.
- **Sahara:** copy this pattern 1:1 — same env-var trick with the Sahara data
  dir, same crafted-file cases (corrupt / empty / good / empty-newest /
  login-only), plus the Sahara seed case (44 items, 3 branches, logins).

### Headless Electron tests — `test.mjs` in each evidence folder (v1.1.9: 15/15; v1.1.10: 24/24, zero console errors)
- **Stack:** Xvfb + real Electron binary + Chrome DevTools Protocol (CDP)
  over WebSocket. No Playwright/Puppeteer — raw `WebSocket` + a `cdp(method,
  params)` helper with a `pending` Map of message ids.
- **Launch:** `Xvfb :99 -screen 0 1280x900x24`; Electron spawned as
  `node_modules/.bin/electron . --remote-debugging-port=<9227|9228> --no-sandbox`
  with `cwd = APP_DIR`, `HOME = <fresh temp HOME per launch>`, `DISPLAY=:99`.
  Fresh HOME per launch (`/tmp/rara-test-1110/home1`, `home2`, …) so
  `userData`, `localStorage` and the data file start clean; relaunching with
  the *same* HOME proves persistence (e.g. the branch choice surviving a
  restart). Pre-seeded HOMEs (crafted `userData` with corrupt data + good/
  empty backups) test cold-start recovery.
- **CDP usage:** poll `http://127.0.0.1:<port>/json/list` for the `page`
  target (10s race timeout on WebSocket open — a stale target can hang
  forever, v1.1.9 lesson); `Runtime.enable` + `Page.enable`;
  `Runtime.evaluate` for assertions/state reads; **real mouse clicks** via
  `Input.dispatchMouseEvent` (`mousePressed` + `mouseReleased` at the
  element's rect — never `element.click()`); `Input.dispatchKeyEvent` /
  `Input.insertText` for PIN/barcode entry; `Emulation.setDeviceMetricsOverride`
  for short viewports (sticky-cart test); `Page.captureScreenshot` → PNG
  saved into the evidence folder.
- **Console-error gate:** `Runtime.exceptionThrown` and `console.error`
  events are collected; the run fails unless the count is **zero**.
  Every run ends with a `PASS/FAIL` per case, a summary line, and a
  `final-run.log`; screenshots are the visual evidence
  (e.g. `login-after-corrupt-recovery.png`, `sale-cart-sticky-scrolled.png`,
  `dashboard-expenses-custom.png`).
- **Regression file:** `regression-119-test.mjs` re-runs the previous
  version's cases (v1.1.10 regression 21/22 — the single "failure" was a
  version assert still expecting 1.1.9, i.e. a stale assertion, not a bug).
- **Commands (from the repo root / evidence folder):**
  `node db-test.mjs` (Node DB tests) and `node test.mjs` (headless Electron;
  starts/kills its own Xvfb + Electron, writes logs + PNGs to the evidence
  folder). No `npm test` script exists — the harness is standalone `.mjs`.
